# Purple Team — Рекомендации

**Класс документа:** Purple Team — Recommendations  
**Классификация:** Internal / учебный  
**Версия:** 1.0  
**Дата:** 2026-01-08  

## 3.1. Цель purple team

Purple team — это не отдельная команда, а **процесс сотрудничества red и blue**. Цель — постоянное измерение и улучшение защитных возможностей.

Основная задача: **сокращать время от атаки к детекту и реакции**.

## 3.2. Ключевые метрики

| Метрика | Описание | Целевое значение |
|---|---|---|
| MTTD | Время до обнаружения | ≤ 15 мин |
| MTTA | Время до подтверждения | ≤ 30 мин |
| MTTC | Время до локализации | ≤ 2 часа |
| MTTR | Время до восстановления | ≤ 24 часа |
| Detection Coverage | Покрытие техник ATT&CK | ≥ 80% |
| False Positive Rate | Ложноположительные | ≤ 5% |
| Time to Deploy Detection | Внедрение правила | ≤ 7 дней |

## 3.3. Модель зрелости

| Уровень | Характеристика |
|---|---|
| 1. Ad-hoc | Реактивные действия, без процессов |
| 2. Managed | Есть playbook, но не тренируются |
| 3. Defined | Регулярные учения, есть метрики |
| 4. Quantified | Есть измерение зрелости и KPI |
| 5. Optimized | Постоянное улучшение на основе данных |

**Рекомендация:** стремиться к 3–4 уровню в течение 6–12 месяцев.

## 3.4. Программа purple team

### 3.4.1. Этап 1. Discovery (1 неделя)

- Составить карту внешней поверхности.
- Определить критичные активы.
- Составить ATT&CK-профиль организации.
- Определить покрытие и gaps.

**Артефакт:** таблица «техника → детект → источник → gap».

### 3.4.2. Этап 2. Baseline emulation (2 недели)

- Провести простые эмуляции без ярких артефактов.
- Проверить, фиксируются ли события.
- Задокументировать results per tactic.

**Артефакт:** отчёт с матрицей «technique → detected → telemetry → quality».

### 3.4.3. Этап 3. Focused scenarios (4 недели)

- Выбрать 3–5 сценариев из RED.md.
- Провести в контролируемом окне.
- Собрать детекты, проверить корреляцию.
- Устранить gaps.

**Артефакт:** обновлённые правила Sigma, EQL, KQL.

### 3.4.4. Этап 4. Continuous loop (постоянно)

- Ежемесячные эмуляции.
- Квартальные учения по ransomware.
- Постоянная калибровка правил.
- Регулярный review модели угроз.

## 3.6. Практические рекомендации

### 3.6.1. Для red team

1. Документировать каждый шаг с **timestamp** и **artifact**.
2. Остановиться при риске повреждения данных.
3. Давать blue team наблюдаемые сигналы, а не «тихие» атаки.
4. Не публиковать эксплойты.
5. Работать в согласованных окнах.

### 3.6.2. Для blue team

1. Фиксировать все источники данных, которые могли бы подтвердить атаку.
2. Не блокировать red team исключениями — наоборот, искать сигналы.
3. Улучшать базовые линии (baselines) для критичных действий.
4. Проверять не только detection, но и response.
5. Обновлять playbook по итогам учений.

### 3.6.3. Для организаций

1. Назначить владельца purple team-процесса.
2. Выделить регулярное окно для учений.
3. Создать библиотеку правил с версионированием.
4. Обеспечить руководство метриками.
5. Строить культуру «учиться на ошибках без поиска виноватых».

## 3.10. Рекомендации по конкретному инциденту

1. **Эмуляция первичного доступа.** Проверить детекты на эксплуатацию внешних сервисов.
2. **Эмуляция «living off the land».** Проверить поведенческие детекты на цепочку `w3wp.exe → cmd → powershell`.
3. **Эмуляция OAuth-persistence.** Проверить, реагирует ли IAM на новые приложения.
4. **Эмуляция отключения EDR.** Проверить self-protection.
5. **Эмуляция SMB-перемещения.** Проверить baseline админ-шар.
6. **Эмуляция выгрузки данных.** Проверить DLP и CASB.
7. **Эмуляция impact.** Проверить, детектируется ли подготовка к шифрованию.
8. **Проверка response.** Тест не только детекта, но и playbook.
